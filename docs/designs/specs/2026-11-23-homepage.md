# Personal homepage for jimmychen.com.au

Status: design v3, 2026-11-23. v3 applies operator feedback after preview (see "Revision 3").
Earlier status: design v2. v2 closes the debate findings D1–D10 listed at the end.

## Spec review

Build a personal site that presents Jimmy Chen through his thinking on AI in
finance and through his software projects. The tone is quiet: plain language and generous whitespace; the visual design is
its own. The site is static and publishes from this repository.

The core need is credibility by demonstration: opinions that are specific
enough to disagree with, and projects described by what they taught rather than
by feature lists.

## Acceptance criteria

1. `npm run build` produces a complete static site in `_site/` with these
   routes: `/`, `/writing/`, one page per article, `/projects/`, `/404.html`,
   `/feed.xml`, `/sitemap.xml`, `/robots.txt`.
2. The homepage is minimal: a hero, three tiles linking to the second-level
   pages (`/finance/`, `/writing/`, `/projects/`) and a contact section.
   `/finance/` and `/about/` hold the detail.
3. Six articles are published as Markdown; accounting practice leads and AI
   is the supporting theme.
4. Four projects are presented with an insight each: AFK (links to its public
   repository), MQT (private; no strategy detail, no repository link), Nestli
   (links to nestliapp.com), and accounting-ledger tooling for AI agents.
5. Privacy invariants hold on every generated file (see the table below).
6. Every HTML page has a unique `<title>`, a meta description, a canonical URL
   under `https://jimmychen.com.au`, and exactly one `<h1>`.
7. Every internal link and asset reference resolves to a generated file.
8. Pages load no third-party resource and ship no JavaScript.
9. The layout works from 320px wide, supports light and dark colour schemes,
   has visible keyboard focus and a skip link, and meets WCAG AA text contrast.
10. `AGENTS.md` is the canonical agent instruction file; `CLAUDE.md` redirects
    to it; `README.md` covers local development, content editing and
    publishing, including the DNS records for the custom domain.
11. A pull-request workflow runs the tests; a deploy workflow publishes `main`
    to GitHub Pages.

## Frozen issue contract

The acceptance criteria above, plus:

**Invariants**

| Invariant | Enforced by | Pinned by |
| --- | --- | --- |
| The only email address on the site is `xin@thechens.au` | single source in `src/_data/site.json` | `tests/site.test.mjs` "only the approved email" |
| No phone number appears | authoring | test "no phone numbers" |
| No link or mention of LinkedIn | authoring | test "outbound links are allowlisted" and "no career or job-seeking language" |
| No job-seeking language | authoring | test "no career or job-seeking language" |
| Outbound links go only to allowlisted hosts and paths | authoring | test "outbound links are allowlisted" |
| No third-party resources, no scripts | templates | test "no scripts or third-party resources" |
| Internal links resolve | templates | test "internal links resolve" |
| No generator or author metadata beyond the site name | templates | test "no generator or author metadata" |
| No employer, client or job-title names | authoring; operator review of the pull request | test "private blocklist", which runs only when `PRIVACY_BLOCKLIST` is set |

The privacy tests read every generated text file (HTML, XML, TXT, CSS, SVG)
with character entities decoded until the text stops changing, not only HTML.
A blocklist failure reports the file and the entry's position only, never the
term, because workflow logs of a public repository are public.

Link rule: `<a href>` to another host must match the outbound allowlist.
Every other reference (`src`, `<link href>` other than canonical and the feed
self-link, CSS `url()` and `@import`) must be same-site.

**Identity rules (operator decision, 2026-11-23).** The site may say: CPA,
Certified ScrumMaster, UNSW, Sydney. It must not name any employer, job title,
employment date, client, suburb or phone number, and must not say or imply that
he is available for work. A committed blocklist would itself publish the names, so the names come from
the `PRIVACY_BLOCKLIST` environment variable (comma-separated). It is set
locally during this work and can be set as an Actions secret; when unset the
test reports itself skipped, and operator review is the remaining control.
Commits use the account's GitHub no-reply address.

**Allowed user-visible behaviour.** The repository goes from an empty README to
a full site. Nothing else exists to change.

**Non-goals.** Contact form, analytics, comments, search, CMS, newsletter,
images or photography, per-project pages, enabling GitHub Pages, DNS changes,
merging to `main`.

**Causal boundary.** Files in this repository only.

## Assumptions

- GitHub Pages serves a custom apex domain from an Actions deployment when the
  domain is set in repository settings; a `CNAME` file is not read in that
  mode. Confirmed against GitHub's custom-domain documentation during the
  debate; not exercised here. The README gives the order: enable Pages and set
  and verify the domain in GitHub first, then point DNS, so the domain is never
  pointed at an unclaimed Pages site.
- DNS is managed at VentraIP (operator, 2026-11-23). The records in the README
  are GitHub's published Pages addresses, from documentation. Risk: GitHub
  changes them; the README links to the source page.
- Eleventy 3.1.x builds on Node 24. Verified during implementation by the test
  suite, which runs a real build through the command line. Node 22 is the
  floor because the test script relies on Node expanding the glob.
- Project descriptions come from the operator's own summary of each project and
  the public AFK README. No metric or outcome is stated that those sources do
  not support.

## Approach

Eleventy 3 with Nunjucks templates and Markdown articles; hand-written CSS; no
client-side JavaScript. Eleventy is the only dependency.

Alternatives considered:

- Jekyll with GitHub's native build. No Ruby on
  the development machine, so the build could not be verified locally.
- Hand-written HTML with no build. Articles would have to be authored in HTML
  and every page would repeat the shell.
- Astro or Next. More machinery than a five-article static site needs.

### Visual direction

A ledger, not a landing page. Warm paper background, near-black ink, one deep
green accent. Serif headings from system fonts, sans body, monospaced tabular
figures for dates and labels. Rules instead of cards: single hairlines between
rows, and the accountant's double underline under totals as the one decorative
motif. The hero carries a small T-account that balances accounting judgement
against software, as real text. Dark scheme inverts to a dark green-black with
a light mint accent. No images, no web fonts, no animation beyond link
transitions that respect reduced-motion.

Reference points for structure and voice, from prior reading rather than
copied: Simon Willison's weblog (dated, plain, link-rich notes), Patrick
McKenzie's Bits about Money (finance explained by a builder), Dan Luu and
Julia Evans (text-first pages), Maggie Appleton (essays plus a projects
garden), Brian Lovin (writing and projects as equal sections).

### Articles

1. AI can draft the journal. It can't own the number.
2. Month-end is a pipeline: where AI helps and where it doesn't.
3. Independence is not optional: what audit teaches about AI review.
4. Models propose, rules dispose: lessons from a trading system.
5. Give the agent a ledger, not a spreadsheet export.

Each is first-person opinion. No employer anecdotes, no invented figures.

## Execution surface

- Writes: the files above. Generated: `_site/` (ignored), by `npm run build`
  (`eleventy`), input `src/`, config `eleventy.config.js`.
- Tests build into a temporary directory by running the Eleventy command line
  and read the output; they write nothing in the repository.
- Executed, not modified: Node, npm, Eleventy, GitHub Actions
  (`actions/checkout`, `actions/setup-node`,
  `actions/upload-pages-artifact`, `actions/deploy-pages`).

## Key implementation notes

- All URLs in templates are root-relative; canonical, feed and sitemap URLs are
  built from `site.url`.
- Dates are authored as `YYYY-MM-DD` and formatted in UTC so the build host's
  time zone cannot shift a date.
- The deploy workflow needs Pages set to "GitHub Actions" as its source. Until
  the operator does that, the deploy job fails without publishing anything.

## Test plan

`node --test` over a real build:

- expected routes exist;
- title, description, canonical and single `<h1>` per page, titles unique;
- internal links and assets resolve;
- only the approved email; no phone numbers; no career or job-seeking
  language; outbound links allowlisted; no scripts or third-party resources;
- feed and sitemap list every article with absolute URLs;
- every article in `src/writing/` and every project in `projects.json` is
  rendered (counts derived from the sources, not hard-coded);
- no generator or author metadata; the private blocklist when
  `PRIVACY_BLOCKLIST` is set;
- `robots.txt` names the sitemap; `CLAUDE.md` points at `AGENTS.md`.

Criteria 9 (layout, contrast, colour schemes) and 11 (workflows) are checked
manually and by the first workflow runs; no automated test pins them. The
tests examine the build, not the deployed site; the live check is manual.

Manual: view the built site in a browser at phone and desktop widths, in light
and dark schemes; check keyboard focus order.

## Revision 3

Operator feedback after previewing v2 (2026-11-23): the style was too heavy in
type and spacing; the homepage should be minimal with content on second-level
pages; accounting and finance should lead, with software and AI as a bonus;
"more Apple style".

Changes, superseding "Visual direction" above:

- Visual: system sans throughout, tight large headings at weight 600, white
  and light-grey surfaces, one blue link colour, rounded tiles, a translucent
  sticky navigation bar, generous whitespace. The serif, the ledger rules and
  the T-account are removed.
- Structure: the homepage is a centred hero, three tiles and contact. New
  pages `/finance/` (practice areas, principles, tools) and `/about/`.
- Positioning: the hero, site description and navigation lead with
  accounting. Projects are framed as side work and reordered so the
  accounting-related one is first. A sixth article on reconciliation, with no
  AI premise, is added.
- Tests: the new routes are required, the homepage must link to each
  second-level page, and inline styles are rejected.

The privacy invariants and identity rules are unchanged.

## Revision 4

Operator feedback on revision 3 (2026-11-23): "too Apple". The structure and
positioning of revision 3 stay. The visual layer changes, superseding the
visual bullet of revision 3:

- Warm paper background, near-black ink and one deep green accent.
- Serif headings at regular weight and moderate sizes; sans body; small
  uppercase labels with open tracking.
- Hairline rules instead of filled tiles; left-aligned layouts; plain
  navigation with no blur or sticky bar.
